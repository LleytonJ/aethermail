## Context

当前删除邮件使用硬删除（直接从数据库移除），用户无法恢复误删邮件。需要实现回收站功能：
- 软删除机制：删除时设置 `deleted_at` 时间戳而非真正删除
- 回收站文件夹：显示已删除邮件
- 恢复功能：从回收站恢复到收件箱或钓鱼邮件箱
- 自动清理：应用启动时清理 30 天前删除的邮件

现有架构：
- 数据库已有 `delete_email` 方法（硬删除）
- Sidebar 已有文件夹列表框架，回收站文件夹已注释掉
- mailbox store 管理 `currentFolder` 和邮件加载

## Goals / Non-Goals

**Goals:**
- 实现软删除机制（`deleted_at` 字段）
- 新增回收站文件夹显示已删除邮件
- 支持恢复到收件箱或钓鱼邮件箱
- 支持从回收站永久删除
- 应用启动时自动清理过期邮件

**Non-Goals:**
- 不实现回收站邮件计数显示（简化 UI）
- 不实现批量恢复/删除（单封邮件操作）
- 不实现 IMAP/POP3 服务器端删除同步（仅本地）

## Decisions

### 1. 软删除字段设计
- **选择**: 使用 `deleted_at INTEGER DEFAULT NULL` 存储删除时间戳
- **原因**: 简单直观，NULL 表示未删除，有值表示已删除
- **替代方案**: 使用 `is_deleted BOOLEAN + deleted_at`，但冗余

### 2. 自动清理时机
- **选择**: 应用启动时执行清理
- **原因**: 简单可靠，不影响运行时性能
- **替代方案**: 后台定时任务，但增加复杂度

### 3. 恢复邮件的目标文件夹
- **选择**: 用户手动选择恢复到收件箱或钓鱼邮件箱
- **原因**: 用户明确知道邮件应属于哪个文件夹
- **替代方案**: 自动恢复到原始文件夹，但原始文件夹信息未存储

### 4. 永久删除触发
- **选择**: 仅回收站邮件显示永久删除按钮
- **原因**: 防止误操作，只有明确进入回收站的邮件才能永久删除
- **替代方案**: 所有邮件都可永久删除，但风险高

## Risks / Trade-offs

- **数据迁移风险** → 现有邮件 `deleted_at` 默认 NULL，兼容性好
- **自动清理可能删错** → 清理阈值设为 30 天，足够缓冲时间
- **回收站邮件同步问题** → 本地回收站，不与服务器同步（文档说明）
- **恢复邮件丢失原状态** → 恢复时重置 `is_phishing` 为目标文件夹类型
