## Goals / Non-Goals

**Goals:**
- 移除无功能的标签模块，消除用户误解
- 实现星标邮件箱，复用钓鱼邮件箱的实现模式
- 保持与现有架构一致性（参考 phishing-folder 实现）

**Non-Goals:**
- 不实现完整的标签系统（此功能可能在后续版本重新设计）
- 不修改星标切换的现有实现
- 不添加星标邮件的批量操作功能

## Decisions

### 决策 1: 星标邮件箱的实现模式

**选择**: 复用钓鱼邮件箱的实现模式

**理由**:
- 钓鱼邮件箱已稳定运行，模式经过验证
- `is_starred` 字段结构与 `is_phishing` 相似
- 代码复用度高，降低风险

**备选方案**:
- 创建全新的文件夹系统架构 → 过度设计，不必要
- 只在收件箱中显示星标图标 → 用户无法快速筛选所有星标邮件

### 决策 2: 标签移除策略

**选择**: 完整删除 TagList.vue 及所有引用

**理由**:
- TagList.vue 仅包含硬编码数据，无任何功能价值
- 保留会误导用户认为功能存在
- 未来重新设计标签系统时可以全新实现

**备选方案**:
- 保留但隐藏 → 代码冗余，维护成本
- 添加 TODO 注释 → 不必要的注释污染

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|----------|
| 用户误以为删除了有用的功能 | 标签从未有实际功能，用户不会受影响 |
| 星标邮件数量实时更新可能影响性能 | 参考 phishing 的 watch 模式，只在切换文件夹时刷新 |
| 取消星标后邮件从星标箱消失需要即时更新 | 监听 toggleStar 成功后刷新列表（可选优化） |

## Migration Plan

2. 添加后端星标查询 API

4. 验证功能完整性

**回滚策略**: Git 分支回滚，无数据库迁移风险（is_starred 字段已存在）
