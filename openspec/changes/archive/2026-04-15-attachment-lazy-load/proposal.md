# 提案：附件懒加载方案

## 背景

当前邮件附件在同步阶段即完整下载并存储到 SQLite 数据库中。这种方式存在以下问题：

1. **带宽浪费** - 无论用户是否需要，所有附件都会下载
2. **存储压力** - 大附件占用大量数据库空间
3. **同步延迟** - 邮件含大附件时同步时间显著增加

## 目标

实现 IMAP 附件懒加载：
- 同步时只获取附件元信息（名称、大小、类型）
- 用户点击时才下载附件内容
- 支持下载进度显示
- 离线时展示元信息并提示需要网络

## 核心决策

| 决策项 | 结果 |
|--------|------|
| 缓存策略 | 保留缓存到固定目录，用户可自行清空 |
| 进度显示 | 显示下载进度条（百分比 + 已下载大小） |
| IMAP 离线处理 | 只展示元信息，提示"需要网络连接" |
| POP3/IMAP UI | 统一体验，不做差异化显示 |
| POP3 风险提示 | 不特殊处理 POP3 缓存清空风险 |
| 下载失败处理 | 删除部分文件，下次重新下载 |
| 预下载策略 | 不预下载，纯懒加载模式 |

## 范围

### 包含

- 数据库模型调整（移除 content BLOB，新增下载状态字段）
- IMAP 客户端新增部分获取方法
- 邮件同步逻辑改造
- 附件下载命令（含进度事件推送）
- 前端附件组件状态展示
- 离线检测与提示
- 缓存管理功能

### 不包含

- 断点续传（复杂度高，暂不实现）
- 小附件预下载
- POP3 特殊风险提示

## 技术方案概览

```
同步阶段 (IMAP):
  UID FETCH BODYSTRUCTURE → 获取 MIME 结构信息
  UID FETCH BODY[1] → 只获取正文
  存入数据库：附件元信息 + is_downloaded=false

下载阶段 (用户点击):
  检查 is_downloaded
    true → 直接返回本地路径
    false → UID FETCH BODY[section] → 下载附件
  发送进度事件 → 前端更新进度条
  保存到缓存目录 → 更新数据库状态

POP3 特殊处理:
  同步时全量下载 → 直接存缓存目录 → is_downloaded=true
```

## 预期收益

| 收益项 | 说明 |
|--------|------|
| 同步速度提升 | 大附件邮件同步时间显著减少 |
| 存储空间节省 | 数据库不再存储附件内容 |
| 用户体验 | 进度条让大附件下载过程可视化 |
| 离线友好 | 离线时可查看附件列表，知道有哪些附件 |

## 风险与缓解

| 风险 | 缓解措施 |
|------|----------|
| IMAP 服务器不支持部分获取 | 检测服务器能力，不支持时回退到全量下载 |
| 网络中断导致下载失败 | 删除部分文件，下次重新下载 |
| POP3 用户清空缓存后无法恢复 | 不特殊处理，主流用户使用 IMAP |
